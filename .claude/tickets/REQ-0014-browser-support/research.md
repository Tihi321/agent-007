# REQ-0014 Browser support: research notes

Date: 2026-11-11. Read-only research. Nothing was built, run or installed (no network, no `yarn build`, tests not run). The repo has no CLAUDE.md. Marks: **C** = confirmed by reading `path:line`; **I** = inferred (reason given).

## Question

How would browser support (R1 full browsing with Playwright + Chromium, R2 isolated persistent profile under the agent data dir, R3 browser work as a Telegram-approved job-runner job with risky actions always asking mid-job, R4 headless with screenshots sent to Telegram and the web UI) fit into the existing job, approval, Telegram, web, settings, packaging and test code? Which places need to change, and what is undecided?

## Answer (short)

1. **Blockers / big findings**
   - The job runner has **no agent loop of its own**. Its engines (`claude`, `dsh`, `hub`) wrap external programs that think for themselves (Claude Code CLI, DeepSeek ACP agent, a PowerShell hub script). The local model that "drives step by step" lives only in the agent process. A browser job therefore needs a decision: who sends the click/type commands (see section 4, options A to D).
   - **Mid-job second approval already works.** `host.askPermission` (manager.ts:557) pushes a Telegram "Allow once / Deny" card while the job stays `running`, and survives an agent restart (permission cards are re-asked from `status`). No new pause/resume mechanism is needed for R3; only a browser-specific "always ask" classifier and a permission `kind`.
   - **No image or file can be sent today, anywhere.** Telegram code only uses `sendMessage` / `editMessageText` / `answerCallbackQuery` (text, no parse mode). `JobDone.artifacts` is always `[]` (manager.ts:836) and only listed as text paths (jobUi.ts:129). IPC lines are capped at 1 MiB (protocol.ts:48), so a screenshot cannot ride inline.
   - **The web UI has no job path at all.** Web chat is for non-owner user bots; `dispatch_job` and all job tools are absent by construction (web/capabilities.ts:7-31), and the CSP is `img-src 'self'` (web/http.ts:12). R4's "web UI" half is new work (owner view of job artifacts) or must be dropped from scope.
   - **The job runner runs as the MAIN user, the agent as a low-priv user (deploy mode).** The runner's data dir is not readable by the agent. So where the profile and screenshots live, and who uploads them to Telegram, is an open decision (section 5/8).
   - Chromium is not in the repo and nothing is downloaded at runtime today. Policy so far: no runtime downloads (windows-exe plan: "There is no download"), `enableScripts: false`, installs ask once, "no network tools in the MVP".
2. **Registering a new job type** touches about 14 places (section 1 list). The `JobEngine` union, `JOB_ENGINES`, the `queues` record, `maxConcurrent`, `engines` config and `loadConventionDrivers` are hard-coded to three names.
3. **Smallest way to do mid-job approval for risky actions**: the driver (or a tool inside it) calls `host.policy.checkPermission` then `host.askPermission` per risky action, like the dsh driver (dsh/driver.ts:371, 395). Nothing else to build on the approval side.

## 1. How a job type is defined, requested, approved, run (end to end)

### Walk-through (Claude job as the example) - all C

1. **Template** (a JSON file the agent cannot edit). Fields in `JobTemplate`, src/jobs/contracts.ts:114-140: `id, title, description, engine, cwd, prompt ({{brief}} slot), params (JSON-Schema subset), permissionMode, allowedTools, disallowedTools, mcpServers, flow, paidModels, autostart, timeoutMin, model, hubService, enabled`. Example: config/templates/list-runs.json. Loaded and validated by `parseTemplate` / `loadTemplates` (src/jobrunner/templates.ts:236-371, 445-477): engine must be in `JOB_ENGINES` (templates.ts:249); non-hub engines must disallow `Bash`/`PowerShell` (272-278), need exactly one `{{brief}}` (284), `cwd` must pass `cwdSyntaxProblem` (255, cwd.ts:36).
2. **Request.** The model calls `dispatch_job {templateId, params, brief}` (src/jobs/tools.ts:282-286, 313-347). `parseJobRequest` rejects any other key (contracts.ts:170-181), `planDispatch` checks template exists/enabled/not hub and validates params (tools.ts:185-228). It creates a durable Pi task `a7.job` (tools.ts:335-339) and returns at once.
3. **Approval card.** Task phase `approve` (src/jobs/task.ts:374-427) builds the card (`buildJobCard`, approval.ts:55-71; lines in `cardLines`, approval.ts:91-106, including "Uses cloud: ..." from `CLOUD_LABELS`, approval.ts:30-34) and `TelegramJobUi.requestJobApproval` sends it with Approve/Reject (jobUi.ts:156-194). Timeout = reject; only an allowlisted user's tap counts (jobUi.ts:362-384).
4. **Submit.** Phase `submit` (task.ts:431-484) sends IPC `submit` `{jobId, request, approval:{userId,at}}`; re-attaches via `status` if the job already exists.
5. **Runner side.** `server.ts` (src/jobrunner/server.ts:174-190) dispatches to `JobManager.submit` (manager.ts:305-376): template lookup, `templateEnabled`, `validateParams`, `checkCwd` against the cwd allowlist/deny list, daily caps, then audit line first, then journal, then queue. `pump()` (623-634) starts jobs per engine under `limits.maxConcurrent(engine)`; `launch()` (636-677) looks up `drivers[rec.engine]`, calls `driver.version()`, then `driver.start(spec)` and iterates `driver.events(jobId)` (run(), 679-728; consume, 730-741).
6. **Driver.** `EngineDriver` (contracts.ts:352-363): `version()`, `start`, `resume`, `events(jobId)` (async iterable ending in `result` + terminal `state`), `cancel`. The core renumbers `seq`/`ts` and applies an output cap (manager.ts:743-764). Claude driver: spawns `claude -p ... --permission-prompt-tool mcp__a7perm__decide --mcp-config <job file>`, brief on stdin (claude/driver.ts:173-262; argv.ts:131-150). The helper MCP (permissionMcp.ts) forwards each non-allowed tool use to the runner with a per-job token, which reaches `handleHelperPermission` (manager.ts:531-555) and the Telegram "Allow once / Deny" card.
7. **Progress and result.** Task phase `run` (task.ts:488-675) follows `job_event` pushes, edits one Telegram status message (jobUi.ts:410-454), relays permission requests (`PermissionRelay`, approval.ts:231-295). Phase `collect` posts the final text once (task.ts:679-716, jobUi.ts:456-471) and stores a wrapped (untrusted) `modelText`; `onSettled` injects it into the model's conversation (phase2.ts:176-180).

## 2. Can a job pause for a second approval mid-run and resume?

**Yes, already (C).**

- Driver or helper asks: `host.policy.checkPermission(ref, tool, input)` returns `allow|deny|ask` (policy.ts:93-101: shell tools denied, Scriptorium denied, Flow budgeted, everything else `ask`). On `ask` the driver calls `host.askPermission(req)` (dsh/driver.ts:371, 395; claude/permissionBroker.ts:110, 126).
- `JobManager.askPermission` (manager.ts:557-595): audits `permission_asked`, stores a pending entry with a timer (`limits.permissionTimeoutSec`, default 1800 s, limits.ts:196-ish), pushes `permission_request` to the agent. The driver's promise stays pending, so the job simply waits in `running`.
- Agent: `PermissionRelay` (approval.ts:231-295) -> `TelegramJobUi.requestPermission` card with **Allow once / Deny only, never "always"** (jobUi.ts:225-275, 385) -> `answerPermission` -> `decidePermission` (manager.ts:519-528) resolves the promise.
- Resume after restarts: pending requests are listed in `status` (`pendingPermissions`, manager.ts:942) and the Job task re-asks them (task.ts:629); `dispose()` aborts cards without answering (approval.ts:261-265). A runner restart makes the job `interrupted` and the task resumes it up to `maxResumes` (2) via `submit {resume:true}` (manager.ts:378-402, task.ts:644-659); resume needs a recorded `engineSessionId` (manager.ts:387), which comes from an `init` event (journal.ts:66).
- Defence in depth: kind `execute` is auto-denied (manager.ts:568-574); a request is denied on timeout, cancel, job end.

**What is missing for browser (smallest additions):**
1. A way to flag "risky" actions: classify per browser action (submit, send/post, pay, file upload, password/credential field fill, navigation to a login or payment URL) in the browser driver or in `CorePolicy.checkPermission` (policy.ts:93); add a `PermissionKind` such as `"browser"` or reuse `"other"` (contracts.ts:262). The card already shows tool, input (cut at 1200 chars, "Show full input") and cwd (jobUi.ts:239-247).
2. "Always ask even if previously allowed": already true; there is no "always" and `allow_once` is per request. Template-level `allowedTools` auto-allow exists only for the Claude engine (argv.ts); a browser driver should not read it, so it cannot be bypassed.
3. Credentials: the card shows the tool input, so a typed password would be shown on Telegram and written to the audit hash line? The audit stores only `inputSha256` (manager.ts:570, 577) but `summary` is `redact()`-ed text of the input (manager.ts:605-613) and the journal/events carry `tool_call` inputs. A browser driver must mask `type`/`fill` values for password fields in its own events and card summary (I: risk, nothing implemented).
4. Let the card also carry the screenshot (see section 3), otherwise the user approves "click #submit" blind.

## 3. How output / artifacts reach Telegram and the web UI; can images or files be sent?

**Today: text only (C).**

- `JobDone.artifacts: string[]` exists (contracts.ts:231) but `JobManager.complete` always writes `artifacts: []` (manager.ts:836). `modelTextFor` and `finalText` just print the list as text lines (task.ts:307; jobUi.ts:129).
- Telegram transport functions use `Pick<Api, "sendMessage" | "editMessageText" | "answerCallbackQuery" | "editMessageReplyMarkup">` (jobUi.ts:35) and `Pick<Api, "sendMessage" | "editMessageText">` (delivery.ts:141). A repo-wide search for `sendPhoto|sendDocument|InputFile|sendMediaGroup` returns nothing. Inbound is text only (`bot.on("message:text")`, telegram/bot.ts:360). All text is sent without parse mode (jobUi.ts:15-16).
- Progress aggregator posts text only (jobs/progress.ts, `ProgressAggregator`); MCP results reduce images to "[image: type, N bytes; content not shown]" (mcp/untrusted.ts:57-60, 66-70), so a local text model never receives an image.
- IPC: one JSON line max 1,048,576 bytes (protocol.ts:48; `encodeLine` throws above it, protocol.ts:255-258) and the runner caps total events at `outputCapBytes` 5 MiB, then cancels the job (limits.ts, manager.ts:758-761). A base64 screenshot in an event is therefore not viable; pass a **file path or id**, never bytes, in events.
- Web UI (C): `src/web/**` has no job or artifact route (grep "jobs" in src/web only hits capability lists and schema `maxJobsPerDay must be 0`, schemas.ts:150). CSP `img-src 'self'` (http.ts:12), static types list `.html .js .css .svg` only (app.ts:74). The UI chat renders markdown only (ui/web/markdown*.js). So "screenshots to the web UI" needs: a new authenticated route that serves PNGs from a per-user/owner dir, an owner-only job/artifact view, and a CSP/MIME change. The web gateway is separate from the job runner and the agent's Telegram host (desktop main.ts supervises `gateway`, `telegram`, `jobrunner` as separate services, desktop/main.ts:34-53).

**Pieces a screenshot path needs (options, not a plan):**
- Telegram: add `sendPhoto` (grammY `InputFile`) to the job transport next to `postProgress`, and an optional `attachments: string[]` on `JobProgressUpdate`/`JobDone`/`PermissionRequest` (contracts.ts:540-557) so the permission card can show the page. The `TelegramJobUi` tests use a fake `JobUiApi` (test/jobs/jobUi.test.ts) that must grow `sendPhoto`.
- File hand-off: runner writes `shots/<jobId>/<n>.png` and puts `{artifacts:[path]}` into the event/`JobDone`. The agent must read it. In **deploy mode** the agent user cannot read the runner's main-user data dir (jobrunner dir ACLs: install-jobrunner.ps1:10-11, 111), and `denyPaths` contains `C:\ProgramData\agent-007` (limits.ts example). In **desktop mode** one user owns everything under `<root>`, with `jobrunner-data` in `denyPaths` for jobs (setup/personal.ts:306) but not for the agent process itself (I: the agent process runs as the same user; the in-process deny list `builtinDenies` covers `config.paths.dataDir`, config/paths.ts:46-57).
- Validation: the agent must only send paths under an allowed artifacts root, check magic bytes/size, and never accept a path from the model.

## 4. How the model drives a job; where browser actions (tools) live

**Facts (C):**
- The job runner does **not** run an agent loop. Claude engine = Claude Code CLI, which has its own model and loop (cloud, subscription); dsh engine = DeepSeek ACP agent (cloud API); hub engine = fixed PowerShell script (`createHubEngineDriver`, hub.ts; manager.ts:693-698 gives `hub` no channel). The model never sees step events during a run except as untrusted wrapped excerpts via `job_status` (tools.ts:349-391) and the final `modelText` (task.ts:304-310).
- The local model (Pi harness, agent process) drives the agent's own tools: `ALWAYS_LOADED` is exactly 10 and fixed (contracts.ts:26-39); everything else is `deferred: true` and found through `tool_search` (extension.ts:156-157; mcp/registry.ts:83-90).
- Agent tools run in the agent process. Their gates: a `beforeTool` hook composed in `composeBeforeTool` (agent/hooks.ts:13-25; shell approval gate approval/gate.ts, Flow guard jobs/flowGuard.ts) and `replay: "unsafe"` marks "never rerun after a crash".
- The agent already speaks to **loopback MCP servers** over Streamable HTTP, wrapping each allowlisted tool as deferred `mcp__<server>__<tool>` with untrusted-content wrapping (mcp/client.ts:56-66; mcp/registry.ts:4-12; config validation requires loopback, config/validate.ts:77). The job runner can start named services after a Telegram card (`hub_start`, mcp/services.ts, manager.ts:464-490).

**Options for where the browser actions live (the planner must choose):**

- **A. Browser engine in the runner + agent-side `browser_*` tools over new IPC ops.** Job = the browser session: approved once on a card (R3 start), runner owns Chromium + profile, agent registers deferred tools (`browser_open`, `_click`, `_type`, `_read`, `_screenshot`, `_close`) that call a new IPC request `browser_action {jobId, action}` (or, to avoid a new type, are carried as a signed MCP-style call). Runner policy classifies each action; risky ones go through `askPermission` (section 2). Local model drives step by step. Needs: row 15 of the checklist, a long-lived job that stays `running` while idle (timeout `timeoutMin`, `maxDurationMin` 360 default, limits.ts), tool-result wrapping as untrusted content (shell/tool.ts `wrapShellOutput`, mcp/untrusted.ts), prompt-injection rules (web text is untrusted). Biggest design, matches R1+R3+R4 best. The `Job task` today waits for a terminal state (task.ts run phase) so progress still posts to Telegram.
- **B. Browser engine with an internal agent loop in the runner** (driver calls a loopback OpenAI-compatible endpoint with `fetch`, as web/chat/openaiEngine.ts does; no Pi import allowed). The job is a fire-and-forget task ("book X") and the runner owns the loop. Needs a prompt, tool-call parsing, loop limits and a model connection from the runner (the runner has no model config today). Largest, and duplicates the harness.
- **C. Template of the existing `claude` engine with a Playwright MCP server in Claude Code's own config.** Zero runner change, the approval/permission path is the existing one (every tool not in `allowedTools` asks; risky browser tools simply stay out of `allowedTools`). But the cloud Claude model drives (page content leaves the PC, subscription terms flag `termsAccepted.claude`), `mcpServers` in a template is only metadata (argv.ts builds `--mcp-config` with the a7perm helper only, claude/driver.ts:206), and the local model is not the driver. Contradicts the "local model drives" idea in the brief; useful only as a stop-gap.
- **D. Playwright MCP server as an agent-side loopback MCP server (no job).** Fits the existing `config.mcp.servers` mechanism, tools appear as `mcp__playwright__*`. No per-call approval exists for MCP tools (only the Flow guard), so R3 needs a new guard in `beforeTool` plus a Telegram card, and it is not a "job" (R3 says job). Could be combined with `hub_start`-style start approval.

Hybrid worth noting (I): A with the runner exposing the actions as a **loopback MCP server per job** (token-scoped like the permission helper, permissionMcp.ts) would let the agent reuse the MCP wrapper code, but the existing client only accepts static config URLs (mcp/registry.ts, config/validate.ts:77), so it needs new wiring either way.

## 5. Data dir, settings and terms gating

### Where things live (C)
- Desktop: root = `AGENT007_HOME` or `%LOCALAPPDATA%\agent-007` (desktop/paths.ts); `personalPaths(root)`: `config\config.json`, `settings\security.json`, `secrets\secrets.json`, `data` (agent data dir, workspace under `data\workspace`) (setup/personal.ts:54-62, 150-152). Job runner: `<root>\jobrunner\jobrunner.json`, data `<root>\jobrunner-data` (secrets, journal, audit, logs, version-guard file), `settingsDir = <root>\settings` (setup/personal.ts:288-306). Ports 47009 gateway, 47007 IPC, 47008 settings UI (desktop/paths.ts).
- Deploy: agent data `config.paths.dataDir`; runner data default `%LOCALAPPDATA%\agent-007-jobrunner` of the MAIN user (limits.ts:~150), config in `C:\ProgramData\agent-007\jobrunner`, security.json in `C:\ProgramData\agent-007\settings`.
- Built-in deny: `config.paths.dataDir` is "in-process only" denied for the agent's file tools except `workspaceDir` (config/paths.ts:46-57), and Claude jobs get Read/Edit/Write deny rules for the runner's deny paths (argv.ts:131-146). So **a profile under the agent data dir is automatically unreadable by `read_file`/`list_dir`** (good for cookies), but it is only used by the runner process if the runner and agent can both reach it.

### Where the Chromium profile should go (decision needed)
- R2 says "under the agent's data dir". Caveat (C/I): the browser process runs in the job runner (main user), whose own dir is `jobrunner-data`. In desktop mode both are under `<root>`: natural choices `<root>\data\browser\profile` (agent data dir, matches R2 wording) or `<root>\jobrunner-data\browser\profile` (main-user only in deploy mode, ACL set by the installer/`writeSecretFile` ACL helper). In deploy mode, the agent user's data dir is not writable by the main-user runner by default (I: ACLs in deploy/setup-agent-user.ps1 / grant-folder-acls.ps1 not read in detail), so `jobrunner-data\browser\...` is the safe default and should be a configurable absolute path in `jobrunner.json` (`engines.browser.profileDir`).
- The profile directory must never be the user's own browser profile: refuse any path under `%LOCALAPPDATA%\Google\Chrome`, `...\Microsoft\Edge` or `User Data` by name in config validation (I).

### Settings schema and forms (C)
- `jobrunner.json` parsing is strict, unknown key = error (`Reader.obj`, limits.ts:101-110, TOP_KEYS 103); engines record at limits.ts:214-227 (per-engine allowed keys are literal: dsh `enabled,verified`; claude `enabled,path`; others `enabled`). A browser engine adds `engines.browser {enabled, channel?, executablePath?, profileDir?, headless?}` and `limits.maxConcurrent.browser`.
- `security.json` (written only by the settings UI of the job runner): `SECURITY_SCHEMA` at settings/schema.ts:113 with sections telegram, model, folders, shell, limits, mcp, jobs, flow, secondOpinion, tools, presets, budgets, proposals, bots, termsAccepted, botBus, botRoom, gate (split table settings/split.ts:17-35; Phase 4 keys line 45). A new top-level section **must** be classified in `KEY_TABLE`/`PHASE4_SECURITY_KEYS` or the migration refuses ("fail closed", split.ts:47-53). Adding e.g. `browser: {allowedDomains[], blockedDomains[], headless, riskyAlwaysAsk}` means: schema entry, split-table classification, a form descriptor in `shippedForms()` (settingsUi/forms/registry.ts:41-80, `securityForm(id,title,sections,extra)`), and the generic renderer needs no code (ui/settings/forms.js renders from schema).
- Budgets exist: `budgets.maxJobsPerDay` default 20 (split.ts `DEFAULT_BUDGETS`) and runner `dailyJobCap` (limits.ts).

### Terms / ack gating (C)
- `termsAccepted` is a security.json section with fixed keys `claude`, `antigravity` (bots/schema.ts:64-65, 181, 313-316), enforced at bot validation (bots/schema.ts:482). It is edited only by the "terms" form, which has `ack: { text }` stored in the audit line, no tool/Telegram path reaches it (settingsUi/forms/phase4.ts:7, 18-19, 48-52).
- A browser acknowledgment ("I understand the agent can act on websites with my logged-in sessions") would be a new key `termsAccepted.browser`, requiring: `TermsAccepted` interface, `TERMS_PROVIDERS`-like list (these are *provider* terms; browser is not a provider, so a separate `browserAccepted` field or its own form with `ack` is cleaner, I), schema, loader, `personalStatus` (setup/personal.ts:258) if shown in the desktop setup page, and the runner refusing the engine (`engineEnabled`) while unaccepted. Desktop setup page only knows `acceptClaudeTerms` (desktop/main.ts:110-125, 455).

## 6. Packaging, Chromium delivery, security policy

### Build and deploy today (C)
- `yarn dist*` = `yarn build` + `scripts/desktop/prepare-node.mjs` (copy signed node.exe; "No download") + `stage-modules.mjs` (`yarn workspaces focus --production` into `build/stage/node_modules`) + `electron-builder --config electron-builder.config.cjs` + `verify-package.mjs` (package.json scripts).
- electron-builder: `app.asar` holds only the launcher (config `files`, electron-builder.config.cjs:12-30); the service tree sits unpacked in `resources/app` via `extraResources`: `dist`, `prompts`, `config` examples/templates, `build/stage/node_modules`, `build/stage/package.json`, `node/node.exe` (lines 31-44). Targets NSIS + portable x64, per-user install, `deleteAppDataOnUninstall: false`.
- `.yarnrc.yml`: `enableScripts: false` (blocks postinstall downloads, e.g. electron's), `nodeLinker: node-modules`. `verify-package.mjs` checks a fixed file list and starts the packaged gateway with bundled node.exe.
- Deploy mode: `deploy/deploy-app.ps1` copies dist/prompts and runs `yarn install --immutable` + `workspaces focus --production` ("downloads from the npm registry: the user runs it knowingly [GO]", deploy-app.ps1:6); jobrunner installer deploy/jobrunner/install-jobrunner.ps1. Scripts follow a dry-run/`-WhatIf` pattern tested in test/deploy*.

### Playwright facts (I - from general knowledge, no network access to verify; verify before planning)
- `playwright-core` is a normal npm package without browsers; with `enableScripts: false` no postinstall could fetch them anyway. Browsers come from `playwright install chromium` (a download of ~150-300 MB into `%LOCALAPPDATA%\ms-playwright`, relocatable with `PLAYWRIGHT_BROWSERS_PATH`) or from a locally installed browser via `launch({ channel: "msedge" | "chrome" })` / `executablePath`. Pinned Playwright versions expect a specific Chromium build, but `channel` works with whatever is installed within reason.
- Persistent profile: `chromium.launchPersistentContext(userDataDir, { headless, channel })`. Playwright's default transport is a pipe to the child (no debugging TCP port), good for the loopback rule.

### Options (the planner chooses, user decides)
1. **Use installed Edge/Chrome binary with a separate profile dir** (`channel: "msedge"` first: Edge ships with Windows 11). No download, no installer growth. "Never the user's own Chrome" is satisfied if it means the *profile* (separate `userDataDir`), but arguably not if it means the *binary*; must be confirmed with the user. The binary updates itself (flaky version coupling, I).
2. **Bundle Chromium** via `extraResources` (add the browser folder to build; installer grows by ~300 MB, needs a pre-build download by the maintainer, a `verify-package` check, set `PLAYWRIGHT_BROWSERS_PATH` for the runner; the signature/SmartScreen story is unchanged since it is unsigned already, windows-exe plan.md:115).
3. **Download on first use** into the runner data dir (user-triggered Telegram/UI "Install browser" button or documented `yarn playwright install chromium` step run by the user [GO]). This is a new runtime-download class; existing policy is "no download" for node.exe (prepare-node.mjs header), installs ask once naming packages (pi-durable-mvp plan.md:176 "Ask once per install, naming the packages and exact versions", 1214), and the agent itself never installs anything (milestone2 plan.md:209 "no installs ... by the agent").

Dependency add: `playwright-core` pinned exactly (project pins exact versions; `save-exact`); it flows into `build/stage` automatically through `workspaces focus --production`, so it ships in `resources/app/node_modules` (I). `npm`/yarn install of a new package needs the user's [GO] per the project rule (plan.md:176, 594).

### Security policy vs a browser reaching the internet
- **What "loopback-only" really covers (C):** the listeners the project owns (job runner IPC/settings UI bind 127.0.0.1 only, limits.ts "no setting for bind address"; web gateway behind Tailscale serve, milestone2 plan.md:82) and URLs the project is configured to *call* (model runners, MCP servers, secondOpinion): `config/validate.ts:59, 77`. Nothing in the repo blocks outbound traffic, and an outbound firewall is listed only as a future idea (pi-durable-mvp plan.md:2123). The job runner already reaches the internet through Claude Code and the DeepSeek API (cloud use, `cloudUse` templates.ts:378). So a browser **is not blocked by the loopback rule**, but it is the first thing that fetches arbitrary web content, and the plan says: "No network tools in the MVP" (plan.md:1413) and "a web fetch tool with an SSRF guard" as a *later* idea (plan.md:2120), with an SSRF guard already written for user bots (`src/web/runtime/ssrf.ts`, header: "No fetch tool ships (UI-41: none)").
- **Reuse (C):** `ssrf.ts` guard (private/loopback/link-local/CGNAT/tailnet ranges, numeric-host tricks, credentials in URL, blocked ports 1234/8080/8787/47007/47008/47009) should wrap every `goto`/redirect target of the browser (also sub-requests via Playwright `route`), otherwise a page can aim the browser at LM Studio (1234), Strata (8080), the proxy (8787) or the project's own IPC/settings UI (47007/47008) and the browser would carry the owner's session. Notably `isLoopbackUrl` allows only 127.0.0.1/localhost for the *project's* calls, the **opposite** requirement for the browser: it must refuse loopback and private ranges.
- **Prompt-injection (C/I):** page text is attacker-controlled. The project treats tool output as untrusted (shell/tool.ts `wrapShellOutput`; mcp/untrusted.ts `wrapUntrustedContent`; job `modelText` wrapped in task.ts:309). Risk I42/I36: a bot on a cloud preset sends tool output to the vendor (pi-durable-mvp plan.md:324); a browser tool must be stripped from cloud-brain bots by default (see `PRIVILEGED_TOOLS = ["shell","dispatch_job"]`, bots/schema.ts:36; `TAINT_BLOCKED_TOOLS`, botbus/capabilities.ts:22: peer-triggered turns must not get browser tools).
- **Isolation at the OS level (I):** the browser would run as the job runner's (main) user with that user's network; profile dir ACL like `jobrunner-data`; Chromium sandbox on; no `--no-sandbox`; downloads disabled (`acceptDownloads: false`) so the browser can't write files to disk, in line with the "downloads" caution.

## 7. Tests: conventions and offline browser testing

### Conventions (C)
- `node:test` against compiled output: `"test": "node --test \"dist/test/**/*.test.js\""` (package.json); `yarn build` first (`tsc -p .`, tsconfig includes `src scripts test`, strict, NodeNext). No test framework dependency. Temp files go under `.claude/temp/` (test/jobrunner/core/helpers.ts header).
- Offline by design: engines are faked. Examples: fake Claude as a node script (test/jobrunner/claude/fakeClaude.ts, scenarios via env), fake ACP agent (test/jobrunner/dsh/fakeAgent.ts), `FakeJobRunnerClient` (test/helpers/fakeJobRunner.ts), fake MCP server (test/mcp/fakeMcpServer.ts), fake OpenAI (test/helpers/fakeOpenAi.ts), core manager tests with a scripted driver (test/jobrunner/core/helpers.ts imports `EngineDriver` fakes), job UI tests with a fake Telegram api (test/jobs/jobUi.test.ts), integration rigs (test/integration/*). Real servers on loopback are used in tests (`createServer`/`listen(0)` in test/web/app.ts, test/mcp/fakeMcpServer.ts, test/proxy/helpers.ts, test/runtime-health.test.ts). `scripts/smoke` and `*-eval` are separate non-unit scripts, not in `yarn test`.
- Pinned lists have tests that must be updated with any new engine/tool: see checklist row 14.

### Browser actions without network (I, design)
- Serve fixture HTML from `http.createServer().listen(0, "127.0.0.1")` in the test (a form with a text field, a submit button, a password field, a page with a redirect to a private IP, a page with a prompt-injection string). Drive it with the real Playwright against a *local* Chromium only in an opt-in test file guarded by an env var (like the smoke scripts), because CI/offline unit runs cannot assume a browser binary is present.
- Default unit tests should use a **fake browser backend** behind an interface (`BrowserBackend { open, click, type, read, screenshot, close }`), same pattern as `fakeClaude`: test the action classifier (risky vs safe), the permission flow (`askPermission` allow/deny/timeout), the SSRF URL guard (pure function, like web `ssrf.ts` tests), parameter validation (strict, unknown keys refused), screenshot hand-off path validation, and the Telegram `sendPhoto` call with the fake api. This keeps `yarn test` offline and deterministic.
- Note the SSRF guard blocks loopback by design, so the fixture-server test needs an explicit test seam (allow list injected) and a separate negative test that proves loopback is refused in the default config.
- A Windows exe check is covered by `verify-package.mjs`; if Chromium is bundled it needs a new file-list check there (I).

## 8. Risks and open decisions for the planner

### Decisions needed from the user (blockers for the plan)
1. **Who drives:** options A/B/C/D (section 4). A is the best fit for R1+R3+R4; B is the "browser job runs alone" reading; C is a stop-gap with a cloud model; D is not a job. Note: "local model drives" is an assumption from the brief; no code in the repo does it yet.
2. **Chromium delivery:** installed Edge/Chrome via `channel` (no download), bundled in the installer (+~300 MB), or first-use download. Also whether "never the user's own Chrome" forbids the installed *binary* or only the *profile*.
3. **Where the profile and screenshots live** (agent `data\browser` vs runner `jobrunner-data\browser`), and how the Telegram-side process gets the PNG when the runner is another Windows user (deploy mode): shared artifacts folder with a narrow ACL, or bytes over a new size-limited IPC reply (needs raising/splitting the 1 MiB line cap), or runner-side Telegram send (runner has no bot token).
4. **Scope of R4 "web UI":** the web UI has no owner job view and no image support; build an owner-only artifact view, or leave it out of this ticket.
5. **What counts as risky:** a fixed list (submit, send, pay, credentials, file upload/download, navigation to a non-allowlisted domain?) and whether *every* `click`/`type` on a page with a form asks. Allowed-domains list and where it is edited (new security.json section vs template params).
6. **Credential handling:** may the agent ever type secrets? Recommended default: never type a password from the model; the user logs in once in a visible (non-headless) window against the isolated profile and the session persists. That conflicts with "headless by default"; needs a "show window" switch and a card.
7. **Acknowledgment:** a new `termsAccepted`-style ack for the browser (extra security.json key + form with `ack`).
8. Dependency approval: adding `playwright-core` (exact version) needs the project's [GO] rule.

### Technical risks
- **One-engine-three-names pattern** (checklist rows 1-9) is brittle: forgetting `queues[...]` crashes `pump` at runtime (manager.ts:193, 625-627), forgetting `maxConcurrent` fails config load.
- **Long-lived idle job vs timeouts/caps:** `timeoutMin` (1..1440 in template, `maxDurationMin` 360 default), `dailyJobCap` 20, output cap 5 MiB per job (screenshots as events would blow it), and the Job task polls `status` every 15 s (task.ts, `pollMs`). A step-by-step session (option A) is far chattier than any current job.
- **One-run assumption:** the Job task has one linear lifecycle `approve -> submit -> run -> collect -> done` and the model's turn ends at `dispatch_job`; for option A the model must call browser tools *while the job runs*. `onSettled` only injects the final result (phase2.ts:176-180). Interleaving needs care (replay safety: browser tools must be `replay: "unsafe"`).
- **Restart behaviour:** a runner restart marks the job `interrupted`; resume needs `engineSessionId` (manager.ts:387); a browser driver has no server-side session, so resume = reopen the persistent profile and lose page state; the permission card for a risky action might refer to a page that no longer exists after resume.
- **Telegram delivery:** `chunkText`/plain-text rules assume text; photo caption limit 1024 chars; rate limits (`withTelegramRetry`, delivery.ts:318); `callback_data` 64-byte rule already handled (`jb:<8hex>:<action>`).
- **Prompt injection / confused deputy:** page content steering the local model into submitting forms; mitigated only by the approval on risky actions and wrapped output. The "ask even mid-job" requirement is the main control; do not rely on the model to flag it. Peer-triggered (bot-to-bot) turns and cloud-brain bots must not get browser tools (I36, I42).
- **SSRF / DNS rebinding / redirects:** guard goto, redirects, sub-resources and `window.open`, block `file://`, `chrome://`, `data:` navigations, set `acceptDownloads: false`, disable extensions and clipboard permissions, no `--remote-debugging-port`.
- **Desktop template gap** (checklist row 11): templates are not copied into the desktop root today; a browser template would not appear for desktop users unless `ensureJobrunner` is extended.
- **Shipping size and `verify-package`:** bundling Chromium changes installer size and the verify list; Playwright version vs Chromium revision pairing.
- **Shared code touched by any new engine:** manager.ts, limits.ts, templates.ts, contracts.ts, protocol.ts (if IPC ops), settings catalogs; ~10 test files pin these lists.
