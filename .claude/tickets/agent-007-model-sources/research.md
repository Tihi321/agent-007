# Research: model sources (all ACP proxy models, LM Studio, "fetch models")

## Question
How should agent-007 offer every model the api-acp-proxy lists (Codex 3, Antigravity 2, Claude 13), LM Studio models, and a "fetch models" step to define any model, following Scriptorium's Models dialog, without breaking the preset invariants (cloud/local, paid/subscription, terms)?

## Answer
- Today a "model" is only a hand-written `PresetConfig` in `security.json` `presets[]`. Nothing creates presets from a fetched list. Only two Claude templates exist (`src/models/templates.ts`). The live `.local/settings/security.json` has 3 presets: strata, claude-sonnet, claude-opus (confirmed).
- agent-007 already fetches the proxy list: `fetchModelIds` (`src/proxy/health.ts:201`) and `checkProxy` (`src/proxy/setupCheck.ts`) return `unusedModelIds`, but it only reports and creates nothing (confirmed). It is used by `src/agent/multibot.ts` only (grep), with no UI call.
- Scriptorium's pattern to copy: a provider registry (base URL, key by env name, local flag), a "Detect models" button doing `GET <base>/models`, a ticked list saved as `picked` (with listed context and price) plus `hidden`, and "Add a model by its id". Fetched data is only a catalogue; the user ticks what becomes usable.
- Proposed design: a **model source** (proxy, LM Studio) plus a **fetch -> classify -> tick -> write presets** flow in the owner settings UI. The classifier fixes `kind`, `privacy`, `providerId`, `billing`, `apiKeyRef` and terms from the source, never from the fetched payload. The web Admin only grants preset ids to users via caps. A real gap: LM Studio presets are single-model per runner block and there is no per-preset model override validation. Details below.

## What the plan needs
Design sketch (options, not a plan):

1. **Source registry.** A small, code-defined list rather than free-form providers (agent-007 is security-first; Scriptorium's free-form "Add provider" is too loose):
   - `acp-proxy`: baseUrl from the existing acp preset or `http://127.0.0.1:8787/v1`, key `proxyApiKey`, fetch via `fetchModelIds` extended to return `owned_by` and group by id prefix (`claude/`, `codex/` or bare, `antigravity/`); health via `fetchHealth` for `auth_method`.
   - `lmstudio`: baseUrl from `model.runners.lmstudio.baseUrl`, key `lmStudioApiToken`, fetch `GET /v1/models` (+ optional `/api/v0/models` for context).
   - (Strata could be a third source with the same shape; `/v1/models` also exists, `runtime/health.ts` header.)
2. **Classification (code, not user or payload).** Table keyed by source plus provider prefix: `acp-proxy/claude` -> `kind acp, providerId claude, privacy cloud, apiKeyRef proxyApiKey, billing subscription` (becomes `paid` only if health says `api_key` AND the owner opts in; MA2 otherwise refuses it), `codex` -> same without terms, `antigravity` -> same with terms. `lmstudio` -> `kind local, runner lmstudio, privacy local`. An unrecognised provider prefix: do not create a preset (`ACP_PROVIDERS` is a closed enum; adding one needs a schema/type change and a decision on its terms).
3. **Fetch.** A new owner-settings route, e.g. `POST /api/models/fetch {source}` (server-side, so the key never reaches the browser; the proxy key is in `secrets.json`, which the settings server would need read access to; check). It returns `[{ref, id, display?, provider, existingPresetId?, proposed: PresetConfig, blocked?: reason}]`. Reuse `matchPresets` to show which are already presets and which unavailable.
4. **Model -> preset mapping.** Deterministic preset id: slug of `<provider>-<model>` shortened to 24 chars with a collision suffix (for example `claude-haiku-45`); existing ids (`claude-sonnet`, `claude-opus`) are reused when the `modelId` matches. Label from the proxy name when known. `contextWindow`/`maxTokens`: defaults per provider/family or a user-entered value (the proxy does not give them), with the 75% compaction (`presets.ts`) depending on `contextWindow`, so a wrong default hurts. LM Studio: use `loaded_context_length` if `/api/v0/models` answers.
5. **Where stored.** Option A (smallest): the UI writes the ticked ones into `security.json` `presets[]` through the existing save protocol (`/api/security/save`, revision + ack), so loader, cross-checks, ceiling and caps work unchanged. Option B: a separate `models.json` catalogue (like Scriptorium's `picked`) merged at load; larger change with a new trust file. Option A fits the current invariants (presets live only in `security.json`, which only the settings UI writes).
6. **UI.** Owner settings UI (`ui/settings/app.js`, Models form): a "Fetch models" button per source, a table (ticks, provider, id, badges cloud/local, subscription/paid, "needs terms", "already a preset"), "Add by id" for a model not listed (the "define any model" requirement), and a Save button that merges selected rows into `presets[]` (+ a prompt to tick the terms for claude/antigravity in the Terms form). The web Admin stays the place to grant presets to users via `caps.presets` (`ui/web/admin.js`); it should only list configured presets. Because `Caps.presets` has `maxItems 20` (`schemas.ts:152`) and `ownerCaps()` is hardcoded (`auth.ts:43`), 18 proxy + LM Studio models exceed or bypass it: raise the limit or derive the owner's caps from the configured presets.
7. **Engine.** No change for the call path: `endpointResolver`/`providersForBot` already handle many presets. Check the Pi `Models` registry for several models under one provider (`providersForBot` already collects `models[]` per provider id), the limiter keyed by `acp-<provider>`, and the gate per runner.
8. **Tests to extend:** `test/bots/*` (validateBotsDoc), `test/models/*`, `test/proxy/*` (matchPresets, fetch parsing), `test/settingsUi/*` (form + routes), `test/web/*` (caps, route). Add: classification table, id slug/length/collision, fetched payload cannot set privacy/billing/key.

## Risks
- Misclassification would break invariants: a fetched proxy model labelled `local` would bypass I42 cloud-safe roots; a Claude model labelled `paid`/`subscription` incorrectly sidesteps MA2 or I58. Classify from the source only; the loader's `validateBotsDoc` stays the backstop.
- Paid vs subscription cannot be read from `/v1/models`. Default `subscription`; an owner must tick "paid" explicitly, and only web bots may use paid (I58). If the proxy reports `auth_method: api_key` for Claude, MA2 refuses the preset unless it is marked paid.
- Terms: all 13 Claude and 2 Antigravity presets need `termsAccepted.claude` / `.antigravity` (already `true` in the live security.json); with the flags off the loader refuses the whole config (not just the route) if a Telegram route lists them. Adding presets only to `presets[]` without putting them in a route is harmless (inferred from the route-only terms check at `schema.ts:~442`).
- Config bloat: a `presets[]` of 18+ entries; `Caps.presets` max 20; `ownerCaps` hardcoded; boot-time-only preset reads need a restart (inferred).
- Proxy models change over time (README: depends on plan and version); stale presets become "unavailable" in `matchPresets`. Need a refresh and a removal story.
- Secrets: the settings server must read `proxyApiKey`/`lmStudioApiToken`; I40 says the key is never pasted into chat and the report redacts it (`discover.ts` header). Do the fetch in the server only, redact errors with `createRedactor`.
- SSRF: the fetch URL must come from the configured loopback `baseUrl` (never the browser). Keep `isLoopbackUrl`.
- The LM Studio runner requires `lmStudioApiToken` even when LM Studio auth is off; fetching models should surface this rather than silently work.
- Gate: Strata and LM Studio share one `RunnerGate` per runner; loading many LM Studio models does not change concurrency, but a second local runner model may trigger a model swap in LM Studio (inferred; LM Studio JIT loading is not verified).
- Exact ids with slashes and spaces: `modelId` is passed through as `claude/sonnet`; confirm the Pi provider/limiter code does not split on `/` (not checked).

## Open questions (for the user)
1. "All models": all 18 proxy models as presets, or fetch-and-tick (recommended; keeps `presets[]` small)? Should Claude's `default` and duplicates (`opus` vs `claude-opus-5`) be offered?
2. LM Studio: only models that are currently loaded, or all downloaded ones? Is one LM Studio host enough (loopback), and does it need the token requirement relaxed?
3. "Fetch models so I can define any model": fetch from the two known sources only, or an arbitrary OpenAI-compatible loopback URL as in Scriptorium's Add provider? Arbitrary URLs would need a new `kind`/privacy class (local-only if loopback) and a decision on keys.
4. Where: owner settings UI (my recommendation) or also the web Admin? Admin today only grants ids to users.
5. Should fetched presets be auto-granted to the owner's caps (`ownerCaps` is hardcoded) and who confirms users' caps?
6. Billing: if Claude uses an API-key login in the proxy, should the fetch offer `paid` presets (web only, with caps), or stay subscription-only?
7. Default `contextWindow` / `maxTokens` per model family, or does the user enter them (U52 says by hand)?
8. Should the Telegram agent need a restart after new presets (today yes, inferred), or should fetch trigger a reload?
9. Preset id naming scheme for new models (max 24 chars, `a-z0-9-`), and keep `claude-sonnet`/`claude-opus` as-is.
