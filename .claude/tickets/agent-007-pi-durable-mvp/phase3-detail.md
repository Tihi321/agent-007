## A. What this revision changes in the outline

1. **Persona schema, validator and `effective()` move into S17.** S17.2 already says "JSON Schema validation for personas", and S18's persona form needs the validator before S19 exists. S19 keeps the runtime (store, apply, guard, overlays, UI, memory).
2. **All `security.json` changes take effect at agent restart** (I25d). The agent holds one immutable snapshot, so there is no mid-turn half-applied security change and no edits to the S2 to S4 code. Prefs and personas are hot. A new `/applysettings` command (S18.4) restarts the agent gracefully.
3. **Prefs are small:** `style {tone, verbosity, language, notes}` and `defaultPersona`. Everything the Phase 1/2 `config.json` held is security (`security.json`) or bootstrap (`config.json`, admin-only). Prefs are not consumed by S4 or S14 code, so no Phase 1/2 file changes.
4. **`propose_*` are non-blocking** (I27a): the tool returns `pending`, the card and its buttons are persisted, and the decision arrives later. No long `beforeTool` wait.
5. **Two persona folders** (I27b): user-authored in `settings\personas\` (written by the UI, main user), model-proposed in `prefs\personas\` (written only after an approved `propose_persona`). The job runner (main user, non-elevated) cannot write the agent profile, so the UI could not otherwise create personas.
6. **A persona's `memoryScope` becomes `memory {write, scope?, sharedRead}`** so "narrower" is well defined.
7. **Prefs, personas and the audit log are validated as untrusted input at every load**, because the agent user owns the prefs files and an approved shell command can edit them (I29c).
8. Added: tamper-evident audit lines (I29a), out-of-band edit detection (I29b), proposal rate limits, a deny-path propagation step so a UI deny edit reaches Claude jobs (S18.3), a Phase 3 mini-eval (S19.7), optional private-chat topics (S19.6).

| Threat | Stopped by |
|---|---|
| The model tries to change an allowlist, a deny path, the approval policy or a runner | No allowlist row (I29d); `get_settings` is read-only; NTFS read-only for the agent user; the agent loader refuses to start if `security.json` or its folder is writable by the agent user (S17.2). |

- [ ] **Residual risks to add:**
  - An approved shell command (agent user) can edit `prefs.json` and model-proposed personas. They cannot widen (validated at load) and the edit is recorded (I29b), but they can change the prompt overlays and memory scope files.
  - If U48a fails and Plan B is not applied, a process-created audit file's owner might rewrite it; the hash chain makes that visible but cannot prevent it, and a removal of the last lines goes unnoticed.
  - The UI runs in the job runner with the main user's full rights. Its blast radius is bounded by the small code surface, the strict input schemas (no eval, no HTML injection), the body limit and the session rules, not by Windows permissions. Malware running as the main user can read a session; out of scope.
